# dsh-evolution

> 面向任务的 skill 自进化插件：让模型为你的环境、偏好和工作流程，生成并维护一套专用技能。

## 这个插件是用来做什么的？

本插件以自动化的 skill 生成和全生命周期管理为目的，主要服务于个性化的能力沉淀场景。它是一个面向任务的插件，一个增强大模型在用户个性化任务上的适配程度的插件。

说得具体一点：你第一次让 Agent 做某件事，往往要解释项目用什么包管理器、发布前跑哪些检查、哪个目录不能碰；做到第十次，这些解释已经稳定了，但模型不会自动知道，你还是得重说一遍。通用模型能学会“怎么发布一个 npm 包”，但学不会“你们仓库发布前必须先跑哪三个脚本、哪个分支不能碰”。本插件要留下来的，就是后面这类只对某个人、某个项目成立的流程知识。

## 什么是 skill？

早期的大模型作为一种自回归语言统计模型，在用户的问题和模型的回复上存在着某种一致性，这就导致通常情况下，越专业的提问方式就能得到越专业的答案，越专业的指令则能引导模型越专业地完成任务，这构成了早期的 prompt 工程。

思维链模式出现后，大模型通常可以在思维链中召回到相关的专业词语和规范，单步任务下的提示词作用被削弱了。但在这之后，大模型又进入了工具调用时代，主要负责的任务从单步的内容生成转向多步的工作调用，此时提示词又一次具备了实际意义，但定位已经和早期不同：相比于早期提示词人物、任务、要求面面俱到的状态，此时的提示词更像是一种操作手册。

不同任务的操作手册很多，不可能一股脑塞进上下文中，因此工业界常用的做法，是按不同的场景给大模型不同的提示词，不同步骤的提示词和大模型输入输出任务串在一起，这也就构成了固定的大模型工作流。而后来，模型能力进一步提升后，大模型已经可以比较准确地根据工具/技能的名称和简介进行选择，此时，把提示词本身也当作一种随取随用的模块成为了一种可能。这种情况下，这种被封装的提示词模块和配套的脚本等工具，就构成了一个 skill。

需要区分的是：MCP 提供的是工具/资源的连接协议，skill 不是 MCP 本身。skill 更像是告诉模型“在这个任务里，何时、按什么顺序、用什么工具、做到什么标准”的那一层。

## 开发本插件的目的是什么？

伴随着大模型能力的进一步增强，出现了以下两个现象：

1、通用且公认好用的 skill（操作手册）被大模型厂商训练成为模型能力的一部分，一句话编程越来越常见，通用 skill 逐渐失去必要性。

2、与此同时，伴随着模型能力的进一步增强，大模型本身已经具备了从历史执行轨迹中总结出质量过关的 skill（操作手册）的能力。

开发者认为，这意味着通用 skill 的退场和专有 skill 的进场。现实中的场景是千奇百怪的，每个用户在日常通过 Harness 调用模型完成任务时，设备环境、个人偏好、复杂任务的流程细节，均存在差异；在通用能力过关之后，大模型需要为每个常常使用它来完成任务的用户，创建专用的 skill（操作）集合，而这个集合的大小，也会随着用户任务的多样性和复杂程度增长。

这种情况下，依赖人力来管理 skill 是不现实的，那么就需要尽可能使用大模型的语义能力，实现语义层面的自动化，解放用户的注意力，包括 skill 的自动化生成和全生命周期管理。

## 与通常情况下的记忆相关插件相比，本插件的定位是什么？

几乎是完全的互补关系。通常意义上的记忆插件会维护一个记忆文件管理系统，其以“事实”为核心管理对象，而本插件则以“流程”为核心管理对象。相比于前者在日常休闲和完成任务中都有帮助的定位，本插件更多的是关注具体的任务流程，是需要使用 Harness 让大模型干活的人所需要的。

另外，本插件也存在着记忆模块，但和专门的记忆插件通常具备的“随取随用，用时检索”“无限增长”等特性相比，本插件的记忆模块是完全背道而驰的。一方面，本插件的记忆模块设有硬字数上限，达到上限后无法写入，只能由模型来决定删除或浓缩哪些已有内容，为新的内容增加空间后才能写入；另一方面，本插件的记忆会全量注入模型上下文。之所以这样设计，同样是因为本插件是任务导向：有一些通用的、最为关键的信息，如果做成随取随用，很可能就不会被大模型看到，进而被遗漏。所以我们希望大模型可以百分之百看到这些信息，且这些信息是长度有限的，既不会因为在上下文中塞了太多东西而导致模型性能损失，又不会带来太多的上下文成本消耗。

## 围绕着 skill，本插件能提供哪些能力？

这些能力不是一条流水线。创建不一定发生在使用之后，复盘不一定产出 skill，整理可能几周都不发生，合并也要等重复积累到一定程度才有意义。把它们排成固定顺序，会让人误以为每一步都必须走一遍。

最自然的起点是写。用户可以说“把这件事写成技能”，模型也可以自己判断某段流程值得留下。创建、改写、打补丁、写支撑文件、归档，都走 `skill_manage`。技能太长时，`restructure` 可以把章节移到 references，`extract` 可以把一部分抽成子技能或引用。写入前有门禁，写入后有版本；删除是归档，不是硬删。

写完以后，问题就变成“下次模型怎么找到它”。默认情况下，插件把技能目录整体发布给平台，模型通过原生的 `skill` 工具按名称加载正文。技能多到一定程度，这种全量目录会变得不划算；这时可以用 `skill_search` 做检索，也可以打开 discovery 的域卡和目录裁剪。但后者不是默认能力：它需要 discovery 开启，还依赖模型和投影条件，默认关闭。所以它解决的是“技能太多以后怎么办”，不是“保证模型每次选对技能”。

技能写下来以后，结构不一定合适。太长、职责太多，就拆；两个技能高度重叠，就合并；旧格式、旧路径、旧章节，就改写或迁移。拆分和改写通常走 `skill_manage` 的写入路径，过门禁、过审批、留版本；`/evolution` 里的 `restructure` 和 `extract` 是另一条命令路径，审批落点不一定和 `skill_manage` 完全一样，这一点以当前实现为准。合并更特殊：它是独立流程，有自己的候选筛选、提交和回执，不走普通写入审批。

再往后，问题不是单个技能的结构，而是整个库的去留。技能多了，总会有不再用的、退化的、重复的。整理器会按时间和空闲条件把过时技能标成 stale、归档，把近重复的合并。它先做快照，失败时只写报告，不会自动把整棵树回滚；需要恢复时用 `/evolution restore`。删除是归档，不是硬删。这一块目前有自动调度和报告，但通知和解释还不完整：整理完成后不一定会在对话里提醒，技能也可能直接从列表里消失。

上面这些动作都可能改坏东西，所以还需要一层控制。这里要解决的不是“用户凭什么相信模型”，而是更实际的问题：模型承担了越来越多的语义判断，用户的注意力和精力又有限，自动化应该停在什么位置。我的想法是，低风险、可回退的动作可以自动做；关键写入可以等人确认；技能写入留版本，删除归档，单技能能撤销，整棵树能回退；写入前有结构门禁、策略保护和威胁扫描。当前实现没有把这件事做满：审批默认关闭，只覆盖可暂存的 memory/skill 写入，整理器和合并器自己的写不经过它；待批主要在有设置页的形态里看得到，通知和收件箱还不完整。

最后是诊断。`/evolution doctor` 能看安装形态、版本、连接和服务状态，但不能证明 memory/skill 工具真的可用；工具是否可用，还是要实际写一次、改一次。健康、漂移、知识图和报告提供的是另一类观察，适合排障和长期维护，不会自动修复问题。

这些能力有使用上的自然顺序，但没有强制流程，也不是同等成熟：写入和版本回退相对完整；检索、域卡、整理通知、合并默认策略、跨形态 UI 还处在基础或条件形态。

## 安装

```bash
dsh plugin --profile web add @lmzhen/dsh-evolution-all
# 重启 dsh，然后在任意会话：
/evolution doctor
```

重启后，让 Agent 记一件事：

> 记住：这个仓库用 pnpm，测试命令是 `pnpm test`。

然后开一个新会话，看这条事实还在不在。先把这一步走通，再试其他功能。

## 四种用法

| 你想怎样 | 装什么 | 实际差别 |
|---|---|---|
| 完整使用 | `@lmzhen/dsh-evolution-all` | 每个会话都有记忆/技能工具，外加设置页和面板 |
| 只要自动化，不要模型写权限 | `@lmzhen/dsh-evolution-host` | 整理、报告照跑；Agent 不能写记忆/技能，review/用量也不生效 |
| 只在部分会话给工具 | `host` + `agent-preset` + `/evolution preset install` | 只有选中 Evolution 预设的会话有工具，其它会话不受影响 |
| 旧的一键配置 | `@lmzhen/dsh-evolution-preset` | 兼容形态；没有设置页和三个侧栏面板 |

**一个 profile 只能挂一种**；换形态先卸载再装。每种形态对会话的精确影响单源在 [packages/INSTALL.md](packages/INSTALL.md)，这里不重复。

## 你实际会用的功能

### 记忆

让 Agent 记住一条事实，或者它自己注意到。它会写 `$DSH_HOME/memories/MEMORY.md` / `USER.md`，新会话自动带一段快照。预算可以在设置里改。

### 技能

让 Agent 把重复流程写成技能。它可以创建、修补、拆分、合并、归档。改错了用 `/evolution skill history <name>` 看版本，`/evolution skill undo <name>` 退回。

### 后台复盘

在自然节点，Agent 回顾刚才发生了什么，给出改进建议。默认在会话内做，不是每句话都打断你。频率可调，也可以关掉。

### 自动整理

整理器定期把过时技能标 stale、把不再用的归档、把近重复的合并。它先快照，删除是归档；用 `/evolution curator status` 和 `/evolution curator report` 看它做了什么。

### 技能合并

两个技能重叠时，Agent 可以提议合并。**默认会自动合并并写入**；打开审批才会等你批准/拒绝。合并结果可以撤销；面板只读，展示队列并复制命令。

### 审批

默认关闭。打开后，只有可暂存的记忆/技能写入会等你批。日常就三条：`/evolution pending`、`/evolution approve <id>`、`/evolution reject <id>`。

## 日常命令

| 命令 | 什么时候用 |
|---|---|
| `/evolution doctor` | 安装/升级后，或怀疑功能没挂上 |
| `/evolution pending` | 看等待审批的写入 |
| `/evolution skill history <name>` | 看/撤销技能改动 |
| `/evolution curator status` | 看自动整理是否到期 |
| `/evolution merge pending` | 看合并提议 |
| `/graph` | 浏览/编辑技能与记忆图 |

还有高级命令（维护扫描、回放、预设安装、章节抽取），在 [docs/commands.md](docs/commands.md) 里；日常不用。

## 值得改的设置

- **审批**：开/关；批准时是否再问一次（只有 all + Web 有设置页）。
- **记忆预算**：项目记忆和用户画像各留多少。
- **复盘频率**：多久回顾一次，或关掉。
- **整理间隔**：多久清理/合并一次。

其它都有合理默认；完整用户向参数见 [docs/configuration.md](docs/configuration.md)。

## 隐私与安全

- 无遥测、无托管服务；数据在 `$DSH_HOME`。
- 模型只能写记忆和技能；内部策略、提示词和审计记录模型改不了。
- 删除技能是归档；恢复和撤销是显式操作。合并有回执。
- 写入前有威胁扫描；审批关着也照扫。

## 已知边界

- **host** 形态没有记忆/技能工具；这是它的用途。要写记忆/技能，用 all 或分层预设。
- 审批默认关闭；要人工闸门就打开。
- 技能健康面板在完整包里默认关闭；它是可选项。
- 需要模型或本地合并模型的功能，失败会明确报错，不会假装成功。

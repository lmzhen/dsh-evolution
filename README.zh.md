# dsh-evolution

> 面向任务的 skill 自进化插件：让模型为你的环境、偏好和工作流程，生成并维护一套专用技能。

## 这个插件是用来做什么的？

dsh-evolution 以 **skill 的自动化生成和全生命周期管理** 为核心，服务于“个人能力沉淀”这个场景。

它不是让模型更会聊天，而是让模型更会按你的方式完成具体任务：你的设备环境、项目约定、操作习惯、复杂任务的流程细节，都会影响一件事该怎么做。通用能力过关之后，模型需要为经常使用它的人，逐步形成一套专用 skill 集合；这套集合会随着任务多样性和复杂度增长，靠人手工维护并不现实。

所以这个插件把 skill 的写入、使用、复盘、修补、拆分、合并、归档、恢复，纳入同一套可审计的管理。它们不是固定顺序，而是围绕不同场景组合使用；关键写入可以选择等待你审批，删除是归档而不是硬删。

## 什么是 skill？

早期的大模型更像自回归的语言统计模型：问题和回答之间存在一致性，越专业的提问、越专业的指令，通常越容易得到专业的结果。这构成了早期的 prompt 工程。

思维链出现后，模型可以在推理过程中自行召回到相关的专业词语和规范，单步内容生成对“面面俱到的提示词”的依赖下降了。但工具调用时代又把问题转了回来：模型的主要工作从“生成一段内容”变成“完成一串操作”，它仍然需要知道先做什么、后做什么、做到什么程度算完成、失败时怎么退。这时的提示词不再像人物设定，而更像一份**操作手册**。

不同任务有不同手册，不可能全部塞进上下文。工业界的做法通常是按场景、按步骤给模型不同的提示词，把输入输出串成固定工作流；而模型具备了根据工具/技能名称和简介选择能力的条件之后，另一种做法出现了：把提示词本身也封装成随取随用的模块。**一个 skill，就是一份被封装的“操作手册”，加上它需要的脚本、模板、参考资料等支撑文件。** 模型在需要时按名称和简介发现它、加载它，再按其中的步骤执行。

需要区分的是：MCP 提供的是工具/资源的连接协议，skill 不是 MCP 本身；skill 更像是告诉模型“在这个任务里，何时、按什么顺序、用什么工具、做到什么标准”的那一层。

## 开发本插件的目的是什么？

模型的进步带来了两个同时发生的变化：

1. **通用 skill 正在被模型能力吸收。** 那些公开、通用、公认好用的操作手册，越来越多地成为模型自身能力的一部分；一句话完成通用任务越来越常见，通用 skill 的必要性随之下降。
2. **模型开始具备从执行轨迹中总结 skill 的能力。** 只要轨迹足够真实、反馈足够明确，模型已经可以从中提炼出质量过关的操作手册。

这意味着：**通用 skill 的边际价值在下降，专有 skill 正在成为差异化能力。**

现实场景是千奇百怪的。每个用户的设备环境、项目约定、个人偏好、复杂任务细节都不同；通用能力过关之后，真正决定任务完成质量的，往往是这些“只对这个人、这个项目成立”的流程知识。它们数量会增长，形态会变化，靠人工整理、命名、去重、归档并不现实。

本插件要做的，就是尽量用模型的语义能力，把这套专有 skill 的生成和生命周期管理自动化；同时用审批、版本、归档和撤销，保证自动化不是失控。

## 和通常的记忆插件是什么关系？

几乎是完全的互补关系。

通常意义上的记忆插件以“事实”为核心管理对象：记住用户是谁、项目是什么、某个决定是什么；它通常在聊天和完成任务时都有帮助。本插件以“流程”为核心管理对象：一件事应该怎么做、按什么顺序做、做到什么标准；它主要服务于**真的要用 Harness 让模型干活**的人。

本插件也有记忆模块，但它的设计与“随取随用、无限增长”的记忆插件相反：

- **有硬字数上限。** 达到上限后，新的记忆写入会被拒绝；模型必须先删除、压缩或合并已有条目，腾出空间，才能写入新的内容。
- **全量注入上下文。** 记忆不做按需检索，而是在会话中完整注入。原因是本插件面向任务：一些最关键、最通用的信息如果做成“需要时再取”，很可能根本不会被模型看到，从而被遗漏。全量注入保证模型百分之百看到它，而硬上限保证注入量有限——既不会因为上下文塞得太满而损害模型表现，也不会带来过高的上下文成本。

这就是本插件的取舍：**记忆宁少勿漏，技能宁专勿泛。**

## 围绕着 skill，本插件可以提供哪些能力？

先把一件事说清楚：**skill 不是一条流水线。** 创建不一定发生在使用之后，复盘不一定产出 skill，整理可能几周都不发生一次，合并只在重复积累到一定程度时才有意义。把它们排成“生成、使用、复盘、修补、拆分、合并、归档、恢复”的先后顺序，会让人误以为每一步都必须按顺序走；实际使用中，它们是不同角色、在不同时间、为不同问题组合起来的能力。

更准确的分法，是按“谁在什么时候、为什么用它”分成几个工作面：

| 工作面 | 谁做/何时 | 产出 | 当前实现的边界 |
|---|---|---|---|
| 写入面 | 用户明确要求，或 Agent 判断流程值得复用 | 新技能、改写、补丁、支撑文件 | 已具备创建/改写/归档；版本与回退是必要配套 |
| 检索面 | 技能数量增长、完整目录不再合适时可选开启 | 搜索结果、域卡、裁剪后的技能目录 | `skill_search` 独立可用；域卡需要 discovery 开启，默认关闭 |
| 结构面 | 技能过长、重叠或格式过旧时按需 | 拆分、合并、迁移后的技能 | 合并是独立流程，不走普通写入审批 |
| 整理面 | 定时/空闲条件满足时 | stale、归档、近重复合并 | 已有自动调度和报告；通知/收件箱仍不完整 |
| 安全面 | 每次写入；审批开启时 | 门禁、审批、版本、撤销 | 审批只覆盖可暂存的 memory/skill 写入 |
| 诊断面 | 排障和长期维护时 | 状态、健康、引用、关系报告 | 只报告，不自动修复；doctor 不能替代实际写入验证 |

六面不是同等完成度：写入面和版本回退相对成熟；检索、域卡、整理通知、合并默认策略和跨形态 UI 仍处于基础或条件形态。这里描述的是能力分工，不是宣称每一面都已完善。

### 1. 把经验写成 skill，或修改已有 skill

这是最核心的写入面，回答的是“这个做法怎么留下来”。

- 用户明确要求“把这件事写成技能”，或 Agent 判断某段流程值得复用；
- 通过 `skill_manage` 完成创建、改写、补丁、归档；支撑文件（references、scripts、templates、assets）也在这里写；
- 长技能可以拆：`restructure` 把章节移到 references，`extract` 把章节抽成子技能/引用；
- 写入前有门禁，写入后有版本；删除是归档，不是硬删。

这一面只负责“写对、写完整”，不负责让模型看到它，也不负责清理旧技能。

### 2. 当 skill 数量增长后，提供按需检索/裁剪的替代模式

这一面回答的不是“模型会不会在该用的时候用”，而是一个更具体的问题：**当自动生成的 skill 越来越多，默认把完整目录交给模型不再合适时，有没有替代模式。**

- 默认情况下，插件把技能树发布到平台的技能目录；模型通过平台原生的 `skill` 工具按名称加载正文。此时默认发布可见技能目录，插件不做按需裁剪。
- 当技能数量增长后，`skill_search` 提供检索；discovery 的域卡/目录裁剪提供另一种组织方式，让模型不必一次看到全部技能。
- 但这不是默认路径：`skill_search` 是独立工具；域卡和裁剪需要 discovery 开启，并依赖模型/投影条件，默认关闭。

所以它属于**条件场景下的可选能力**，不是“每次任务都帮你选对技能”的保证。模型这次没加载某个技能，可能是描述不够清楚、触发条件不匹配，或者任务根本不需要它；这些不能一律归因于插件。插件能做的是提供目录、正文、检索和裁剪，执行仍由模型和它调用的工具完成。

### 3. 对已有 skill 做结构性重构

这一面回答的是“技能已经写下来了，但结构不合适怎么办”。它不是日常流水线的一步，而是按需发生的编辑。

- **拆分**：一个技能太长、职责太多时，拆成父技能和子技能，或把细节移到 references；
- **合并**：两个技能高度重叠时，合成一个更完整的技能；
- **改写/迁移**：把旧格式、旧路径、旧章节结构整理成当前可用的形态；当前主要通过改写/补丁完成，不是独立的迁移引擎。

通过 `skill_manage` 的拆分和改写走普通写入的门禁、审批和版本；`/evolution` 的 restructure/extract 是另一条命令路径，审批落点以当前实现为准，不应假设与 `skill_manage` 完全一致。合并是独立流程，有自己的候选筛选、提交和回执，当前不受普通写入审批覆盖。合并不等于“生命周期结束”，只是对重复结构的一次重构；它们通常发生在技能积累到一定规模之后，而不是每个技能都必须经历。

### 4. 让整个 skill 集合保持可用

这一面回答的是“技能多了以后，哪些还有用、哪些该退场”。

- 使用记录（查看、修补、支撑文件读取）提供证据；
- 整理器按时间/空闲条件把过时技能标 stale、归档，把近重复的合并；默认不会硬删；
- 固定/保护标记设计上用于阻止某些技能被整理；具体覆盖范围以当前实现为准；
- 健康检查、漂移检查、知识图提供不同角度的观察，但它们只报告，不自动修复。

整理器和重构的区别是：**重构改变一个/一组技能的结构；整理决定技能集合里谁留下、谁退场。** 合并只在“有重复”时发生，整理则在“长期不用/结构退化”时发生，二者不是同一条流水线上的前后步骤。

当前实现已经有定时整理和报告，但通知/解释并不完整：整理完成后不一定会在对话里提醒，技能也可能直接从列表里消失。这一面目前更接近“后台执行 + 报告”，还不是完整的收件箱体验。

### 5. 在语义自动化和用户注意力之间取得平衡

这一面回答的不是“用户凭什么相信模型”，而是一个更实际的问题：**当模型承担越来越多的语义判断，而用户的精力和注意力有限时，怎样让自动化停在用户愿意承担的范围内。**

设计上的分工是：

- 低风险、可回退的动作可以自动完成，避免用户为每个细节做审批；
- 关键写入可以选择人工确认，把注意力留给真正需要决定的时刻；
- 技能写入留下版本，删除是归档，单技能可撤销，整树可回退；
- 写入前有结构门禁、策略保护和威胁扫描；
- 报告和诊断尽量解释“发生了什么”，而不是让用户从结果反推。

但当前实现并没有把这件事做满：审批默认关闭，只覆盖可暂存的 memory/skill 写入，整理器/合并器自己的写不经过它；待批主要在有设置页的形态里看得到，还没有完整的通知/收件箱；可解释性也更多落在报告和命令上，而不是每个动作都有面向用户的解释。这里描述的是设计方向与当前覆盖范围，不是宣称平衡已经完成。

### 6. 观察与诊断

这一面回答的是“现在到底怎么了”。

- `/evolution doctor` 看安装形态、版本、连接和服务状态；它不能证明 memory/skill 工具真的可用，工具是否可用仍要实际写一次/改一次来验证；
- 健康/漂移/图/报告看结构、引用、使用和关系；
- 它们适合排障和长期维护，不是日常任务入口，也不替代实际写入验证。

**一句话总结分工：写入面负责“把做法留下来”，检索面负责“技能多了以后还能找到”，结构面负责“把已有技能整理成合适形状”，整理面负责“决定谁留下”，安全面负责“让这一切可回退”，诊断面负责“解释发生了什么”。** 这六面可以单独使用，也可以组合，但不是必须按顺序走完的六个阶段。

## 安装

```bash
dsh plugin --profile web add @lmzhen/dsh-evolution-all
# 重启 dsh，然后在任意会话：
/evolution doctor
```

重启后，让 Agent 记一件事：

> 记住：这个仓库用 pnpm，测试命令是 `pnpm test`。

然后开一个新会话，这条事实已经在了。最小的闭环就是：**记住、复用、改进**。

## 四种用法

| 你想怎样 | 装什么 | 你会得到 |
|---|---|---|
| 完整体验（推荐） | `@lmzhen/dsh-evolution-all` | 每个会话都有记忆/技能工具，外加设置页和面板 |
| 只要自动化，不要模型写权限 | `@lmzhen/dsh-evolution-host` | 整理、报告照跑；Agent 不能写记忆/技能，review/用量也不生效 |
| 只在部分会话给工具 | `host` + `agent-preset` + `/evolution preset install` | 只有选中 Evolution 预设的会话有工具，其它会话不受影响 |
| 旧的一键配置 | `@lmzhen/dsh-evolution-preset` | 兼容形态；没有设置页和三个侧栏面板 |

**一个 profile 只能挂一种**；换形态先卸载再装。每种形态对会话的精确影响单源在 [packages/INSTALL.md](packages/INSTALL.md)，这里不重复。

## 你实际会用的功能

### 记忆

让 Agent 记住一条事实，或者它自己注意到。它会写 `$DSH_HOME/memories/MEMORY.md` / `USER.md`，新会话自动带一段快照。预算可以在设置里改。

### 技能

让 Agent 把重复流程写成技能。它可以创建、修补、拆分、合并、归档。改错了用 `/evolution skill history <name>` 看版本，`/evolution skill undo <name>` 退回。

### 后台复盘

在自然节点，Agent 回顾刚才发生了什么，给出改进建议。默认在会话内做，不是每句话都打断你。频率可调，也可以关掉。

### 自动整理

整理器定期把过时技能标 stale、把不再用的归档、把近重复的合并。它先快照，删除是归档；用 `/evolution curator status` 和 `/evolution curator report` 看它做了什么。

### 技能合并

两个技能重叠时，Agent 可以提议合并。**默认会自动合并并写入**；打开审批才会等你批准/拒绝。合并结果可以撤销；面板只读，展示队列并复制命令。

### 审批

默认关闭。打开后，每次记忆/技能写入都等你批。日常就三条：`/evolution pending`、`/evolution approve <id>`、`/evolution reject <id>`。

## 日常命令

| 命令 | 什么时候用 |
|---|---|
| `/evolution doctor` | 安装/升级后，或怀疑功能没挂上 |
| `/evolution pending` | 看等待审批的写入 |
| `/evolution skill history <name>` | 看/撤销技能改动 |
| `/evolution curator status` | 看自动整理是否到期 |
| `/evolution merge pending` | 看合并提议 |
| `/graph` | 浏览/编辑技能与记忆图 |

还有高级命令（维护扫描、回放、预设安装、章节抽取），在 [docs/commands.md](docs/commands.md) 里；日常不用。

## 值得改的设置

- **审批**：开/关；批准时是否再问一次（只有 all + Web 有设置页）。
- **记忆预算**：项目记忆和用户画像各留多少。
- **复盘频率**：多久回顾一次，或关掉。
- **整理间隔**：多久清理/合并一次。

其它都有合理默认；完整用户向参数见 [docs/configuration.md](docs/configuration.md)。

## 隐私与安全

- 无遥测、无托管服务；数据在 `$DSH_HOME`。
- 模型只能写记忆和技能；内部策略、提示词和审计记录模型改不了。
- 删除技能是归档；恢复和撤销是显式操作。合并有回执。
- 写入前有威胁扫描；审批关着也照扫。

## 已知边界

- **host** 形态没有记忆/技能工具；这是它的用途。要写记忆/技能，用 all 或分层预设。
- 审批默认关闭；要人工闸门就打开。
- 技能健康面板在完整包里默认关闭；它是可选项。
- 需要模型或本地合并模型的功能，失败会明确报错，不会假装成功。

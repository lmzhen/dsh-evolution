# dsh-evolution

> 给 DeepSeek Harness 做 skill 的自动生成和长期管理。

## 这个插件是做什么的

它服务的是“用 Harness 干活”的人，不是闲聊场景。

通用模型已经能处理很多标准任务，但每个人手上的项目、机器、习惯和流程都不一样。一个任务该先做什么、用什么工具、哪里容易出错、什么算做完，这些细节通常不在通用能力里。dsh-evolution 想管的，就是把这些细节沉淀成 skill，并在之后的使用中继续修、继续整理。

所以它不是“让模型更聪明”的插件，也不是一个通用 skill 市场。它更像一套个人 skill 的生成和维护机制：模型从实际任务里总结做法，写成 skill；下次遇到同类任务时再拿出来用；用得多了、放久了、重复了，再决定怎么整理。

## 什么是 skill

skill 不是模型，也不是 MCP。MCP 解决的是“模型能连到什么工具”，skill 解决的是“这个任务该怎么做”。

早期做提示词，大家会把人物、任务、要求、格式都写进去。思维链出来以后，单步生成对这套写法的依赖小了很多，模型自己能在推理里补上不少专业词汇和规范。但工具调用又把问题拉回到流程上：模型要连续做很多步，仍然需要知道顺序、边界、检查点和失败后的退路。这个时候的提示词，更像一份操作手册。

手册不能全塞进上下文。按场景拆、按步骤拆，是常见做法；模型能根据名称和简介选工具之后，另一种做法是把手册本身也做成一个可以按需加载的模块。一个 skill 就是这种模块：一份写给模型看的操作说明，加上它需要的脚本、模板、参考资料。模型在需要时按名称找到它、加载它，再照着做。

## 为什么做这个插件

有两个变化值得放在一起看。

一个是通用 skill 的价值在下降。公开、通用、大家都知道怎么写的操作手册，正在被模型能力本身吸收；一句话完成通用任务越来越常见，单独维护一份通用 skill 的收益越来越小。

另一个是模型开始能从执行轨迹里总结 skill。轨迹足够真实、反馈足够明确时，模型可以写出一份质量不错的手册。

这两件事放在一起，结论不是“skill 没用了”，而是“通用 skill 的边际价值在下降，专有 skill 的价值在上升”。每个用户的设备、项目、偏好和任务细节都不同，真正影响完成质量的，往往是这些只对某个人、某个项目成立的流程知识。它们会越来越多，也会变形、重复、过时；靠人手工命名、整理、去重、归档，不现实。

这个插件想用模型的语义能力把这件事接过去，但自动化不等于放任：写入要有门槛，删除要能恢复，关键动作要允许人插手。

## 和记忆插件是什么关系

基本是互补的。

记忆插件管“事实”：用户是谁、项目是什么、之前定过什么。它聊天时有用，干活时也有用。这个插件管“流程”：一件事该怎么做、按什么顺序做、做到什么标准。它主要服务于真的要用 Harness 完成工作的人。

这个插件也有记忆模块，但设计方向和“随取随用、无限增长”的记忆插件相反。

它给记忆设了硬上限。写满之后，新的内容写不进去；模型得先删掉、压缩或合并旧条目，腾出空间再写。它也不做按需检索，而是把记忆完整注入上下文。原因很直接：这是任务型插件，最关键的那些信息如果做成“需要时再取”，很可能根本不会被模型看到。全量注入保证它看到，硬上限保证注入量有限，不至于把上下文撑坏，也不至于花太多 token。

取舍就是：记忆宁可少一点、完整一点；skill 宁可专一点，不要泛。

## 围绕 skill 的能力

这些能力不是一条流水线。创建不一定在使用之后，复盘不一定产出 skill，整理可能几周都不发生，合并也要等重复积累到一定程度才有意义。把“生成、使用、复盘、修补、拆分、合并、归档、恢复”排成固定顺序，会让人误以为每一步都必须走一遍；实际不是这样。

更实际的分法，是看它们各自解决什么问题。

### 写 skill，改 skill

这是最核心的一块。用户可以说“把这件事写成技能”，模型也可以自己判断某段流程值得留下。创建、改写、打补丁、写支撑文件、归档，都走 `skill_manage`。技能太长时，`restructure` 可以把章节移到 references，`extract` 可以把一部分抽成子技能或引用。写入前有门禁，写入后有版本；删除是归档，不是硬删。

这块只负责把 skill 写对、写完整。它不负责让模型看到，也不负责清理旧技能。

### 技能多了以后，怎么让模型找得到

默认情况下，插件把技能目录整体发布给平台，模型通过原生的 `skill` 工具按名称加载正文。目录里有多少技能，模型就能看到多少摘要；插件不做按需裁剪。

技能多到一定程度，这种“全量目录”会变得不划算。这时可以用 `skill_search` 做检索，也可以打开 discovery 的域卡和目录裁剪，让模型不必一次看到全部技能。但后者不是默认能力：它需要 discovery 开启，还依赖模型和投影条件，默认是关闭的。

所以它解决的是“技能太多以后怎么办”，不是“保证模型每次选对技能”。模型没加载某个技能，可能是描述不清楚、触发条件不匹配，也可能这个任务本来就不需要它。插件能提供目录、正文、检索和裁剪；执行还是模型和工具的事。

### 拆分、合并、改写

技能写下来以后，结构不一定合适。太长、职责太多，就拆；两个技能高度重叠，就合并；旧格式、旧路径、旧章节，就改写或迁移。

拆分和改写通常走 `skill_manage` 的写入路径，过门禁、过审批、留版本。`/evolution` 里的 `restructure` 和 `extract` 是另一条命令路径，审批落点不一定和 `skill_manage` 完全一样，这一点以当前实现为准。合并更特殊：它是独立流程，有自己的候选筛选、提交和回执，不走普通写入审批。

这些操作通常发生在技能积累到一定规模之后，不是每个技能都必须经历。

### 整理技能库

技能多了，总会有不再用的、退化的、重复的。整理器会按时间和空闲条件把过时技能标成 stale、归档，把近重复的合并。它先做快照，失败时只写报告，不会自动把整棵树回滚；需要恢复时用 `/evolution restore`。删除是归档，不是硬删。

固定和保护标记的用途，是让某些技能不进入自动整理；具体覆盖范围以当前实现为准。

整理和拆分、合并不是一回事。拆分、合并改的是一个或一组技能的结构；整理决定的是整个技能集合里谁留下、谁退场。合并只在有重复时发生，整理则在长期不用或结构退化时发生。

这一块目前有自动调度和报告，但通知和解释还不完整。整理完成后不一定会在对话里提醒，技能也可能直接从列表里消失。它更像“后台执行加报告”，还不是一个完整的收件箱。

### 写入控制与回退

这里要解决的不是“用户凭什么相信模型”，而是更实际的问题：模型承担了越来越多语义判断，用户的精力和注意力又有限，自动化应该停在什么位置。

我的想法是，低风险、可回退的动作可以自动做；关键写入可以等人确认；技能写入留版本，删除归档，单技能能撤销，整棵树能回退；写入前有结构门禁、策略保护和威胁扫描。这样用户不用审每一件小事，但真出事时能退回来。

当前实现没有把这件事做满。审批默认关闭，只覆盖可暂存的 memory/skill 写入；整理器和合并器自己的写不经过审批；待批主要在有设置页的形态里看得到，通知和收件箱还不完整；可解释性更多在报告和命令里，不是每个动作都有面向用户的解释。

这些是现在的边界，不是设计上不想要。

### 诊断

`/evolution doctor` 能看安装形态、版本、连接和服务状态。它不能证明 memory/skill 工具真的可用；工具是否可用，还是要实际写一次、改一次。

健康、漂移、知识图和报告提供的是另一类观察：结构、引用、使用情况、技能之间的关系。它们适合排障和长期维护，不是日常入口，也不会自动修复问题。

这几块能力可以单独用，也可以组合着用。它们不是六个必须按顺序走完的阶段，也不代表每一块都已经做到同样的完成度。写入和版本回退相对成熟；检索、域卡、整理通知、合并默认策略、跨形态 UI 还处在基础或条件形态。

## 安装

```bash
dsh plugin --profile web add @lmzhen/dsh-evolution-all
# 重启 dsh，然后在任意会话：
/evolution doctor
```

重启后，让 Agent 记一件事：

> 记住：这个仓库用 pnpm，测试命令是 `pnpm test`。

开个新会话，看这条事实还在不在。先把这一步走通，再试其他功能。

## 选哪种装法

| 你想怎样 | 装什么 | 实际差别 |
|---|---|---|
| 完整使用 | `@lmzhen/dsh-evolution-all` | 每个会话都有记忆/技能工具，带设置页和面板 |
| 只要后台自动化 | `@lmzhen/dsh-evolution-host` | 整理、报告能跑；Agent 不能写记忆/技能，复盘和用量不生效 |
| 只在部分会话给工具 | `host` + `agent-preset` + `/evolution preset install` | 只有选中 Evolution 预设的会话有工具 |
| 从旧配置迁移 | `@lmzhen/dsh-evolution-preset` | 接近 all，但没有设置页和三个侧栏 |

一个 profile 只能挂一种；换形态先卸载再装。具体差异在 [packages/INSTALL.md](packages/INSTALL.md)，这里不重复。

## 日常怎么用

记忆这条线很简单：让 Agent 记住一条事实，或者它自己觉得值得记。内容写在 `$DSH_HOME/memories/MEMORY.md` 和 `USER.md`，新会话自动带一段快照。预算在设置里改。

技能这条线，是让 Agent 把重复流程写下来，创建、修补、拆分、归档都行。改坏了用 `/evolution skill history <name>` 看版本，`/evolution skill undo <name>` 退回。删除是归档，不是硬删。

复盘和整理在后台跑。复盘会在任务收尾时多跑一轮，默认累计约 10 次工具调用才触发；觉得烦就调大间隔或关掉。整理器会按时间和空闲条件把过时技能归档、把重复的合并；它先快照，删除是归档。整理完不一定会在对话里通知你，想看结果用 `/evolution curator status` 和 `/evolution curator report`。

合并是另一条线。两个技能重叠时可以合成一个；默认会自动接受并写入，想每次确认就打开 `mergeApproval`。它需要本地合并模型，不会自动下载。合并是独立流程，不走普通写入审批。

审批默认关闭。打开后，只有可暂存的记忆/技能写入会等你批准；整理和合并自己做的写不经过它。日常用 `/evolution pending`、`/evolution approve <id>`、`/evolution reject <id>`。

## 常用命令

| 命令 | 什么时候用 |
|---|---|
| `/evolution doctor` | 装完、升级后，或怀疑功能没挂上 |
| `/evolution pending` | 看等待审批的写入 |
| `/evolution skill history <name>` | 看/撤销技能改动 |
| `/evolution curator status` | 看自动整理是不是到期 |
| `/evolution merge pending` | 看合并队列 |
| `/graph` | 浏览/编辑技能与记忆图 |

高级命令（维护扫描、回放、预设安装、章节抽取）在 [docs/commands.md](docs/commands.md)，日常不用背。

## 设置

常改的只有四类：

- 审批开/关，以及批准时要不要再问一次；
- 项目记忆和用户画像各留多少字符；
- 复盘多久跑一次，或者关掉；
- 整理间隔。

设置页只有 all + Web 有；host、preset、分层没有，只能走命令或改 profile。完整参数在 [docs/configuration.md](docs/configuration.md)。

## 隐私和安全

没有遥测，也没有托管服务；数据都在 `$DSH_HOME`。

模型能写记忆和技能，但改不了内部策略、提示词和审计记录。技能删除是归档，恢复和撤销都要显式操作。写入前会做威胁扫描，审批关着也照扫。

## 已知边界

- host 没有记忆/技能工具，这是缩配；要写记忆/技能，用 all 或分层预设。
- 审批默认关闭；打开也只覆盖可暂存的记忆/技能写入。
- 技能健康面板默认关闭，是可选项。
- 需要模型或本地合并模型的功能，失败会明确报错，不会假装成功。
